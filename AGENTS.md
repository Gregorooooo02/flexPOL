# HedgeFlex (Finance Quest challenge)

## Learn investing. Practice safely. Build confidence.

## 1. Concept

**HedgeFlex is our entry for the Finance Quest challenge: a gamified financial-learning application that combines Duolingo-style lessons, an AI learning coach, and a fictional investing sandbox.**

Users follow a learning path, complete short quizzes and practical missions, then unlock an open sandbox where they can experiment freely or compete in goal-based challenges.

The aim is to help people move from knowing financial concepts to confidently applying them. This matches the official challenge's focus on bridging financial knowledge and action for self-directed investors. [Challenge...Quest.pdf | PDF]

## 2. Target learner and learning objective

**Proposed initial learner:** a beginner self-directed investor who understands some terminology but is unsure how to make an investment decision.

**First mission's learning objective:**

> Given a fictional goal, investment horizon, and liquidity needs, the learner can choose an allocation and explain its tradeoffs.

Across the broader product, scenarios can reflect different life stages, goals, circumstances, and experience levels, as required by the challenge's generational theme. [Challenge...Quest.pdf | PDF]

## 3. User journey

| Stage | User experience |
|---|---|
| **Start** | Select experience level and a fictional goal. |
| **Learn** | Complete short explanations and interactive questions about investing concepts. |
| **Practice** | Allocate virtual money among fictional instruments in a guided mission. |
| **Experience consequences** | Encounter a simulated market change or unexpected need for money. |
| **Reflect** | Get an AI explanation of the tradeoffs and answer a reasoning question. |
| **Improve** | Adjust the allocation and compare the alternative outcome. |
| **Unlock** | Enter Free Play or a competitive Quest Arena. |

## 4. Main features

### Learning path

- Short chapters covering concepts such as risk, diversification, time horizon, and liquidity.
- Quizzes with explanations, not just correct/incorrect feedback.
- Progress indicators, XP, and mastery badges.

**Chapter plan and lesson content:** all learning content lives in the [knowledge/](knowledge/) folder. Start with the overview, [knowledge/learning-chapters.md](knowledge/learning-chapters.md), which lists chapters, subchapters and missions. Each chapter has its own folder with one file per subchapter, holding the lesson for the user and control questions with answers. Read these before working on lesson content, quizzes or missions. Sandbox scenarios for Chapters 2 and 3 (seeded into the database, listed on `/scenarios` with a brief page each, playable at `/scenarios/{id}/play`) are in [knowledge/sandbox-scenarios.md](knowledge/sandbox-scenarios.md); their values (instruments, amounts, horizons, targets, scoring weights) are in [knowledge/sandbox-scenarios.json](knowledge/sandbox-scenarios.json), the source of truth when the two differ. Scenarios are built for the Playground workspace and the batch simulation (catalogue instruments plus 0% cash, horizons up to 3,650 days); after changing the JSON, run `node scripts/check-sandbox-scenarios.mjs`, which validates it and checks on many seeds that each reference allocation scores at least 80 and each trap at most 50, then `node scripts/generate-content-sql.mjs` to update the seed.

### AI coach

- Explains unfamiliar concepts in accessible language.
- Gives hints before revealing an answer.
- Discusses the learner's choices in the context of the mission.
- Helps the learner reflect and improve.

**Boundary:** the AI is an educational coach, not a personal investment adviser. It should not invent simulation outcomes or scoring rules.

### Investing sandbox

A small set of fictional instruments with clearly stated properties, such as:

- Accessible cash.
- A diversified market basket.
- A volatile concentrated asset.
- A locked-term instrument.

All prices, events, and outcomes are explicitly synthetic. Choices are evaluated against the goal and constraints, rather than teaching that one instrument is universally "right."

### Two sandbox modes

- **Free Play:** experiment, replay scenarios, and consult the coach without ranking.
- **Quest Arena:** compete using the same starting budget, mission, constraints, and simulated events.

### Goal-based leaderboard

Reward **goal alignment, resilience, concept application, and improvement**, rather than simply the highest return. Use transparent rules for scoring, with the AI explaining the result.

## 5. Recommended hackathon MVP

The official brief requires a prototype demonstrating **one complete learning mission**, plus a clear target learner, learning objective, and evidence of understanding and engagement. [Challenge...Quest.pdf | PDF]

**Build this complete vertical slice:**

> One short lesson → quiz → portfolio allocation → simulated event → AI debrief → retry → score → sandbox unlock.

| Include in MVP | Leave for later |
|---|---|
| **One learner scenario and learning objective** | Full personalized curriculum |
| **One complete chapter** | Many chapters and instruments |
| **A few fictional instruments** | Real products or live market data |
| **One authored simulation scenario** | Complex market simulation |
| **Context-aware AI coaching** | Fully autonomous AI-generated lessons |
| **Simple scoring and leaderboard** | Seasons, leagues, and social features |
| **Basic Free Play using the same engine** | Extensive sandbox customization |

If leaderboard entries are fictional demo users, label them clearly.

## 6. Suggested workstreams

| Workstream | Main deliverables |
|---|---|
| **Learning content and UX** | Mission story, lesson, questions, explanations, screen flow, accessible language. |
| **Frontend** | Learning screens, allocation controls, results, coach interface, progress, leaderboard. |
| **Simulation and backend** | Instrument definitions, scenario events, balance calculations, scoring, saved progress. |
| **AI integration** | Coach prompts, structured mission context, grounded explanations, fallback responses. |
| **Testing and demo** | End-to-end walkthrough, calculation checks, AI boundary tests, presentation story. |

**First shared dependency:** agree on the mission and data contract before building independently. Define the goal, instruments, learner choices, simulated events, scoring rules, and information passed to the AI.

## 7. What success looks like

By the end of the demo, the learner should be able to:

- Explain why their allocation fits, or does not fit, the mission.
- Recognize a tradeoff revealed by the simulation.
- Improve their decision after feedback.
- Identify what they still need to understand before taking a real-world step.

**Pitch:**

> **HedgeFlex turns financial learning into an interactive adventure. Learn the basics, test your decisions with virtual money, get guidance from an AI coach, and compete on the quality of your plan, not just your luck.**

This summary keeps your original learning-path and sandbox idea intact, while narrowing the prototype to one complete experience and making the competition support learning rather than speculation.

  Quiz responses contain questions and A–D options only. Correct answers and explanations are left out on purpose: they are only revealed by the answer endpoint (`QuestionService`), after the learner has picked an option.
- Current learner (mock login, no real authentication): requests name the learner with the `X-User-Email` header (`controller/UserHeader`), matched case-insensitively. `UserService.findCurrentUser` / `requireCurrentUser` resolve it inside the caller's transaction; an email with no user returns 401 ("log in again"), and so does a missing header where a learner is required (`UnauthorizedException`, mapped by `ApiExceptionHandler`). The header proves nothing, so anyone can act as any email: fine for the demo only.
- Quiz attempts (`QuizAttemptService`): the frontend starts an attempt when the learner begins a quiz's questions and sends its `attemptId` with each answer. Only the first answer to each question is saved (`attempt_answer` is unique per attempt and question), so practice retries don't change the score. When every question has an answer the attempt is completed: `score` counts correct first answers and `passed` is `score >= passMark`, or always true for quizzes without a pass mark (control quizzes). Later answers are still checked but not saved. Another learner's attempt returns 404, and a question from a different quiz returns 400.

- **`knowledge/` is the source of truth for content.** The block between the `GENERATED CONTENT` markers in `data.sql` is generated from it: after changing anything in `knowledge/`, run `node scripts/generate-content-sql.mjs` from the repository root and commit the updated `data.sql`. - **Duel scenarios (no playable Duel yet):** `knowledge/duel-scenarios.json` holds versioned, neutral competition templates, rules, disclaimers and curated budget/horizon pairs. The same content-generation command validates it and writes `backend/src/main/resources/duel-scenarios.json` (a generated classpath resource, not SQL; commit it and never edit it directly). It rejects duplicate template IDs/options, unknown fields/categories, blank text, non-EUR currency, non-positive or sub-cent budgets, budgets above the simulation cap, and horizons outside 1–3,650 days. `DuelScenarioService` validates content at startup and resolves an immutable `DuelScenarioSpec`; match creation persists it once for both participants, rather than regenerating on each request. It selects only `STOCK`/`EQUITY_ETF` templates with at least two eligible EUR catalogue instruments, excludes missing/unregistered simulation models, and uses the engines' shared `validateParameters` hook to reject malformed supported configurations without simulating. If no configured category is available, generation fails explicitly. The spec snapshots the category's ordered instrument IDs and display metadata; `DuelScenarioResponse.from(...)` and `frontend/src/model/duel.ts` expose the public brief without simulation parameters or seeds. Visible template randomness is separate from future hidden-market randomness. See `notes/duel-implementation-plan.md`.
- **Duel match/planning lifecycle:** `DuelMatchService.createMatch(firstUserId, secondUserId)` remains an internal entry point for future matchmaking, not a public arbitrary-opponent endpoint. Tables `duel_match`, `duel_participant` and `duel_allocation` store one UUID match with a versioned JSON scenario snapshot, two unique learners/seats, revisioned EUR allocation drafts, submission timestamps/sources and deadlines. Creation locks both user rows in ascending ID order and checks active participation; all subsequent access takes the match-row write lock. The inner service receives the already-resolved learner ID from `DuelApiService`, returns 404 for another learner's match, and exposes only that learner's portfolio plus both display names/submitted flags (no opponent allocations/emails). `DuelMatchResponse`/`DuelPortfolioRequest` have matching types in `frontend/src/model/duel.ts`. Draft replacement validates revision, snapshotted whitelist, unique IDs, positive whole-cent amounts and the shared budget; cash is derived. A stale revision/locked phase raises `DuelConflictException` (409 problem details with the recipient's current snapshot). Manual submit atomically saves a nonempty full plan and locks it; repeats return the existing submission without accepting a new plan.
- **Duel REST boundary:** `DuelController` exposes participant, queue and ticket routes above. `DuelApiService` resolves `UserService.requireCurrentUser` from the demo header, never from a body/query learner ID. Its short write transactions use `noRollbackFor = DuelConflictException.class`, preserving automatic timeout/replay/settlement changes even when a late command returns 409. `/me` initializes/reads the rating, then makes bounded recipient-only reference queries without match reconciliation after the profile's user-row lock. `DuelPhase.ACTIVE_PHASES`/`TERMINAL_PHASES` are shared by creation/recovery. Queue/ticket operations use nontransactional `DuelQueueApiService` plus short `DuelQueueDirectory` database boundaries; queue work is forbidden inside an outer transaction. `DuelHttpConfiguration` applies `Cache-Control: no-store` before binding on REST routes, including conflict/error bodies; the handshake sets it separately. `DuelInputExceptionHandler` maps malformed UUID/JSON/missing required query parameters to safe RFC 9457 400s without echoing input; global advice handles 401/404/409/429. Success responses are 200; no arbitrary-opponent creation route exists. The header is still spoofable demo identity, not real authentication. Service tests and temporary real-HTTP walkthroughs verify identity, recovery, private output and transaction guarantees.
- **Duel deadlines/replay:** injected UTC `Clock` plus `hedgeflex.duel.briefing-duration=8s` and `hedgeflex.duel.planning-duration=120s` define persisted deadlines; durations must be positive and at most one day. `DuelCoordinator` scans at most 100 due IDs every `hedgeflex.duel.coordinator-delay=500ms`, advances each in a separate short transaction, then dispatches pending evaluations. `hedgeflex.duel.coordinator-enabled=false` disables both lifecycle and matchmaking scheduled adapters for controlled tests. Reads/commands also reconcile deadlines after locking, so no client timeout callback or scheduler punctuality is required. Phases are `BRIEFING` → `PLANNING` → `EVALUATING` → `EVALUATED` → `REPLAY` → `FINISHED`, with terminal `CANCELLED`/`EMPTY_PORTFOLIO` or `FAILED` alternatives. At exactly `planningEndsAt`, missing submissions freeze their last accepted draft with source `TIMEOUT`; empty/all-cash drafts cancel the game. Both early manual submissions advance immediately. Evaluation commit sets `replayStartsAt` once with `hedgeflex.duel.replay-lead-in=2s`, and `replayEndsAt` with `hedgeflex.duel.replay-duration=10s` (both positive, at most one day). `EVALUATED` is the lead-in; at replay end settlement marks `FINISHED`. Reads/reconnects never reset deadlines, and late processing catches up in one transaction. Conflicts do not roll back committed logical transitions. Cancelled/failed/finished learners can explicitly join again; replay stays active until settlement. No Duel UI exists yet. The single-instance queue/sockets and H2 matches/results/ratings all disappear on restart.
- **Duel FIFO/presence:** `DuelQueueService` uses generation-tagged entries in insertion order, with a short mutex and reservations retained through creation/recovery. The directory's five-second independent creation transaction calls `DuelMatchService.createMatch`; no database calls, scenario generation or socket sends run under the queue mutex. A dedicated one-thread/no-backlog worker scans every `hedgeflex.duel.matchmaking-delay=500ms`, at most eight pairs per pass. `hedgeflex.duel.matchmaking.queue-lease=30s` and `.heartbeat-interval=10s` control presence (positive millisecond durations, at most five minutes; heartbeat shorter than lease). Duplicate join preserves priority, stale live-entry commands conflict, and missing heartbeats never implicitly rejoin. Leave while reserved records intent: a committed match wins, but failed creation removes the leaver and preserves the partner's FIFO position. Persisted active participation is authoritative; uncertain outcomes retain reservations until readable, with a two-second retry backoff. Max 1,000 in-memory entries, including short-lived matched tombstones. Closing a socket does not cancel queue membership immediately or affect match deadlines. `DuelQueueServiceTests` cover FIFO/idempotence, exact expiry, stale IDs, a leave/create race, failure priority and uncertain-commit recovery.
- **Duel WebSocket:** `/api/duels/ws?ticket=...` uses native WebSocket, no STOMP/SockJS. The handler mapping precedes REST `/{matchId}` so `/ws` is not parsed as a UUID. A random 192-bit ticket is bound to the resolved learner, one-use and valid for `hedgeflex.duel.matchmaking.ticket-lease=30s`; global outstanding-ticket/connection caps are 4,096/1,000, with five tickets and five active-or-handshaking connections per learner. Set `hedgeflex.duel.matchmaking.allowed-origins` to explicit production HTTPS app origins; defaults allow localhost/127.0.0.1 ports 5173/8080. Wrong origins get 403; missing/expired/replayed tickets get 401. Peers cannot choose recipients/subscriptions or send commands. Only text `ping` is accepted for liveness, answered by a `PONG` notification; native idle timeout is 60s. Async container sends serialize a 32-message per-peer buffer with a five-second send limit; broken/slow peers deregister and close asynchronously via a bounded executor. `DuelTicketRedactionFilter` removes ticket values from application URI/parameter logging and retained socket URIs. Container/reverse-proxy access logs must omit queries (`%U`, not query-bearing request lines); do not log request attributes or credentials. Deploy behind HTTPS/WSS with Upgrade forwarding and an idle timeout longer than 60s. Tickets do not fix mock authentication.
- **Duel notifications:** `DuelEvents` emits immutable recipient-ID/revision data via an `AFTER_COMMIT` listener. `MATCH_FOUND`, `MATCH_CHANGED`, `QUEUE_CHANGED` and `RATING_CHANGED` are invalidation hints; fetch REST snapshots after reconnect/missed/out-of-order events. Draft saves notify only their owner, submission/phase/evaluation/settlement notify both participants; no seeds, portfolios, emails or chart streams are sent. Queue-only changes publish outside queue/database locks. A late 409 that commits a timeout still notifies; rolled-back creation/drafts do not. `DuelEventsTests`/`DuelRealtimeServiceTests` cover commit/rollback delivery, privacy, one-use/expired tickets, caps, slow-peer buffers and send deadlines. A temporary real-client walkthrough verified direct and Vite-proxied upgrades, private pairing, third-user queuing, reconnect, stale cancellation, expiry, an offline player's timeout and exactly-once settlement.
- **Frozen Duel market and evaluation:** creation stores a private `DuelMarketSpec` JSON alongside the public brief: an independent `SecureRandom` seed, UTC creation-date anchor, horizon, EUR 1,000,000 canonical base, valuation version, and every whitelisted instrument's frozen engine key/version/parameters. `SimulationService.freezeDefinition`/`simulateFrozen` reuse the existing engine registry without catalogue lookups during evaluation; the latter rejects unavailable engine versions, shortened horizons, negative/unordered points and any mismatch in interior point dates. Public simulation endpoints are unchanged. `DuelEvaluationService` runs with `Propagation.NEVER`, simulates the union of held IDs once, and values both allocations against those same paths: `roundHalfEven(allocation × baseValue / baseAmount)` per holding, then add constant 0%-earning cash. Returns and maximum drawdown are fractions; `returnDifferencePercentagePoints` is the absolute final-value gap divided by budget × 100. Higher final cents wins even when both lose; exact ties draw. `DuelResult` stores one immutable, versioned JSON payload per match (match PK/FK), with shared dates, both allocations/curves, contributions, cash, profit, returns, drawdown and outcome. `DuelMatchService.getResult(matchId, learnerId)` releases it at `EVALUATED`, `REPLAY` or `FINISHED`; otherwise 409, or 404 for another learner. Planning snapshots continue to hide opponent holdings. Matching public types are in `frontend/src/model/duel.ts`.
- **Duel evaluation delivery/recovery:** `DuelEvaluationWorker` uses a dedicated two-thread executor with no waiting task queue. Each delivered job is claimed in a short `DuelEvaluationJobService` transaction and calculated outside it; a second transaction atomically inserts the result and changes the phase. Claims use random tokens, `hedgeflex.duel.evaluation-lease=30s` and `hedgeflex.duel.evaluation-max-attempts=3` (1–5); lease durations must be positive and at most one day. Expired claims can be retried with the identical frozen market, never a new seed; exhausting leases gives `FAILED/EVALUATION_TIMEOUT`. Calculation/configuration errors fail immediately with `EVALUATION_ERROR`, without an outcome or point changes. Both complete/fail callbacks require the current unexpired token; duplicate/late workers cannot overwrite a result. Input JSON/model details and seeds are not exposed in DTOs or worker logs. `DuelEvaluationJobServiceTests` and `DuelEvaluationServiceTests` cover immutable-market replay after catalogue changes, result privacy/idempotence, competing/expired claims, bounded retries, shared-price rounding, draws, negative-return winners and explicit failures. Frozen simulation service tests cover replayability and interior-date mismatch rejection.
- **Duel points/settlement:** `DuelRatingService.getRating(userId)` lazily initializes `duel_rating` at 1,000 points for any existing learner, including demo users. Match creation ensures both accounts exist under the existing ascending user-row locks and freezes formula version `duel-gap-v1`. For a non-draw, `rawTransfer = 10 + min(30, roundHalfUp(300 × abs(finalValueA - finalValueB) / budget))`; a draw transfers 0. `appliedTransfer = min(rawTransfer, loserCurrentPoints)`, so the winner gains exactly what the loser loses and neither account goes negative. Replay completion holds the match lock, locks both existing rating accounts in ascending user ID order (no user-row locks during settlement), and atomically updates balances, inserts two `duel_rating_change` audit rows unique per match/user, stores formula/raw/applied metadata on the match and marks it `FINISHED`. Draws/zero-floor wins still have two zero-delta audit rows; cancelled/failed matches have none. `DuelMatchService.getSettlement(matchId, learnerId)` is participant-only (404 otherwise), returns 409 until finish, then returns immutable before/delta/after balances and whether the loser floor reduced the transfer; it never recalculates past balances from current accounts. Login DTOs remain unchanged; profiles/settlements are exposed through the Duel API. `DuelRatingResponse`, `DuelSettlementResponse` and new replay timestamps have matching frontend model types. `DuelRatingServiceTests` cover exact boundaries, normalized formula/rounding/cap, floor and zero-point losers, draws, late catch-up, historical stability, concurrent finalization, rollback atomicity and cancellation/failure without transfers.
- The H2 console is at `http://localhost:8080/h2-console`.
- AI coach (`CoachService`): set the `OPENAI_API_KEY` environment variable to enable it, and optionally `OPENAI_MODEL` (default `gpt-5-mini`). Never commit the key. Without a key, or when the OpenAI call fails, the app still starts and the endpoint returns a fixed fallback reply with `aiAvailable: false`. The system prompt is `src/main/resources/prompts/coach-system.md`; it keeps the coach educational (no personal advice, no invented simulation results or scoring). When `subchapterId` is given, that lesson's Markdown is added to the system prompt as a template parameter. Only chat is used: embedding, image, audio and moderation models are turned off with `spring.ai.model.*=none`. Tests replace OpenAI with a stub `ChatModel` bean (`CoachControllerTests`), so they never call the network.
- Coach conversation memory: the first message without `conversationId` starts a conversation and the response returns its new UUID; sending it back continues the conversation. Ids that are not UUIDs return 400; an unknown UUID just starts empty. `MessageChatMemoryAdvisor` adds the last 20 messages (Spring AI's `MessageWindowChatMemory` default) to each prompt and saves the new question and reply. Only learner and coach messages are stored; the system prompt and lesson context are added fresh on each call. Storage is the JDBC chat memory in the same database (table `SPRING_AI_CHAT_MEMORY`, created by Spring AI's own schema script on embedded databases), so with in-memory H2 conversations are lost on restart. Ownership (`CoachConversationService`, table `coach_conversation`): a conversation started with `X-User-Email` belongs to that learner, and anyone else, or a request without the header, gets 404 for it. An unknown UUID sent by a learner is claimed by them and starts empty. Conversations started without the header stay unowned, as before the mock login.
- Coach question context (`CoachContextService`, read-only transaction so the model call holds none): with `questionId`, the system prompt gets the question, its A–D options, the quiz type, and rules for how much the coach may reveal. It mirrors what the quiz screen shows: before an answer, hints only in a practice (`CONTROL`) quiz and no hints at all in a scored (`FINAL`) test; after a correct answer, the explanation; after a wrong practice answer, why the pick does not fit but not the correct option; after a wrong test answer, the correct option and explanation (the screen already shows them). The correct option is never in the prompt before the learner has an answer that reveals it. `selectedOptionId` is the learner's checked option; it must belong to the question (404 otherwise).
- Commands: `./mvnw spring-boot:run` starts the app; `./mvnw test` runs the tests.
- Instrument catalog/detail/history GET endpoints and `POST /api/simulations` are implemented. Simulations run on demand without persistence; `GBM` uses configured drift/volatility and a reproducible seed, and `FIXED_RATE` supports ACT/365 accrual with STOP-at-maturity behavior. The current seed contains only market instruments; no deposit fixture is API-selectable yet.
- Simulation requests and responses use `durationDays` (1–10,950 calendar days, approximately 30 years) and support positive investments up to EUR 1,000,000,000,000, rounded to cents. Requested end dates use `startDate.plusDays(durationDays)`; fixed-rate product maturity still uses `termMonths`. Unknown instruments return 404; undefined/out-of-bounds inputs return 400. Model/configuration failures do not silently fall back to another engine.
- GBM uses a calendar-day horizon but emits the initial point and weekday points, skipping intermediate weekend dates. If the end date is a weekend, one terminal carry-forward point is included without a random draw. A 10-day request from 20 November 2026 ends on 30 November and returns 7 points, not 10 or 11.
- `POST /api/simulations/batch` simulates several instruments over one shared timeline (used by the planned Playground workspace). The body is a JSON array of the same `SimulationRequest` (1–50 items, distinct `instrumentId`s, one shared `durationDays` of 1–3,650); the response is an array of `SimulationResult` in request order, and all results must share the same start and end date or the call fails. An item without `randomSeed` gets an independent seed: `SeedMixer` (SplitMix64, masked to 53 bits so it is exact in JavaScript) derives it from a per-request master seed and the instrument ID. An explicit seed is used as given, so the same seed on two items gives them identical shocks, which means perfect correlation. Every result returns the seed actually used, so one item can be replayed through `POST /api/simulations`. Instruments move independently (no correlation). A 20-instrument, 5-year batch is about 1.3 MB of JSON.
- Error mapping: unknown instruments return 404 (`ApiExceptionHandler`), and invalid simulation input (`IllegalArgumentException`) returns 400 through a handler scoped to `SimulationController`.
- Run `bash mvnw test` from `backend/`. The current tests cover application startup, learning content and its repository, the quiz answer endpoint, the AI coach, batch simulation (`SimulationServiceTests`: independent and replayable seeds, shared timeline and order, explicit seeds, invalid batches), the seeded scenarios (`ScenarioServiceTests`: order and brief, rules, unknown id), and scenario runs (`ScenarioRunServiceTests`: all-cash run paying a need from cash, same market on every run and needs sold from holdings, the rule limit boundary, rejected allocations).
- Scenario runs (`ScenarioRunService`, not transactional; `ScenarioService.getRunSpec` reads the brief plus the server-only seed in its own read-only transaction): each invested instrument goes through `SimulationService.simulateBatch` with seed `scenarioSeed + instrumentId`, so every learner and retry gets the same market (an all-cash run simulates one allowed instrument only for the timeline). The evaluation follows `knowledge/sandbox-scenarios.md` §4 and mirrors `scripts/check-sandbox-scenarios.mjs`: money needs are paid at the first point on or after their day, from cash first, then by selling the same fraction of every holding; the largest drop is measured on value plus money paid out (the money actually paid, so a shortfall doesn't soften it); growth is 0 after a shortfall; rules are checked exactly (`amount > maxShare × budget` breaks a rule, the limit itself doesn't). The seed and the reference/trap allocations are never returned.

## Testing policy

Keep testing minimal unless the user asks for more.

- **Default: test the service layer only.** When adding or changing backend behaviour, write JUnit tests for the affected `service/` classes. Do not add controller, repository, MockMvc/integration or frontend tests unless the user explicitly asks for them.
- **Keep test cases few and focused.** Cover the happy path and the key edge cases of each changed method (for example a boundary value, a rejected input, or an invariant the code must keep). Do not write exhaustive matrices, many near-duplicate cases, or tests of trivial getters and mappings.
- **The frontend has no test runner and gets no tests by default.** Verify frontend changes with `npm run build`, `npm run lint` and a manual check. Do not add a test dependency unless the user asks.
- **When the user asks for more testing, do exactly what they specify** (for example more cases, a different layer, or a new tool), and update the Tech stack tables if a dependency is added.
- Existing tests stay in place and must keep passing; this policy governs new work.
